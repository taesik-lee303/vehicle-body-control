## 1. 핵심 개념

### 1.1 QA vs V&V (p.23-27)
- 품질 확보 = 프로세스 품질(QA) + 제품 품질(V&V). QA는 "프로세스가 지켜지는지 + 산출물이 요구를 만족하는지" 확인하는 활동(p.25).
- **Verification(검증)**: "제품을 올바르게 만들고 있는가" - 요구사항 명세서대로 구현했는지. **Validation(확인)**: "올바른 제품을 만들고 있는가" - 고객 의도/사용 목적에 맞는지 (Boehm, p.27).
- 시스템 테스트(SWE.6)까지 = Verification, 인수 테스트(VAL.1) = Validation (p.241).
- **VBC**: 우리 `tests/test_*.c` + `docs/verification.md`는 SRS(VBC-SRS-001) 대비 *Verification*. 가상 환경이라 Validation(실차 의도 적합성)은 범위 밖임을 verification.md에 명시할 것.

### 1.2 용어: Mistake -> Fault -> Error -> Failure (p.36-39)
| 용어 | 의미 | 예 |
|---|---|---|
| Mistake(실수) | 사람이 결함을 주입하는 행위 | 종료 조건을 잘못 이해 |
| Fault/Defect/Bug(결함) | 코드/문서 속 잘못된 상태 | 반복 종료 조건 오류 |
| Error(오류) | 명세 결과와 처리 결과 불일치 | 10회여야 하나 무한루프 |
| Failure(고장) | 상위 시스템 요구 기능 수행 실패 | Watchdog 리셋, ECU 멈춤 |
- 모든 결함이 고장을 일으키진 않음(실행 안 되는 경로의 결함, p.37). 결함은 "명세 위반/명세에 없는 동작/해야 하는데 안 하는 것"까지 포함(p.38).
- 예제 `doubleFunc`: `param*param`은 입력 2는 우연히 통과(2*2=4=2+2)하고 입력 1에서만 실패 - **입력 2만 쓰면 결함 은폐**(p.37). 테스트 입력은 우연히 맞는 값을 피해 선택.

### 1.3 테스트 원리 7가지 (p.44-45)
1. 결함 존재를 보일 뿐 부재를 증명 못 함 2. 완벽한 테스트 불가(기법/우선순위/리스크 기반) 3. 초기 시작(Shift Left, p.7-8: 후기 수정은 40~1000배 비용) 4. 결함 집중(파레토 80/20) 5. 살충제 패러독스(같은 TC 반복 -> 효력 감소, TC 갱신) 6. 정황 의존 7. 오류 부재 궤변
- "Art of Software Testing" 원칙(p.45): **작성자와 다른 그룹이 테스트**(객관성), 결함 발견이 목적, **비정상/예외 입력도 테스트**, 결함 많은 곳에 더 테스트, TC 체계적 관리/재사용, 결과 철저 점검.
- **VBC**: "author != verifier"의 근거. 살충제 패러독스 -> 요구사항 변경 시 TC도 갱신.

### 1.4 정적 vs 동적 (p.41-43, 49-51)
- **정적**: 실행 없이 결함 발견(리뷰, 정적분석, 메트릭). 요구/설계/코드/테스트 케이스 문서 모두 대상. 초기 비용 절감, 지식 공유, 동적으로 못 잡는 결함(도달불가 코드, 미정의 변수, 표준 위반, 인터페이스 불일치) 식별(p.50-51).
- **동적**: 실행해서 입력->기대출력 비교(p.140). 목적은 "결함이 있음을 보임"이며 현실적 목표는 "주어진 자원으로 결함 발견 확률이 높은 TC 선택"(p.140).
- V-모델에서 정적 테스트는 요구~코딩, 동적은 단위->통합->시스템->인수 (p.43).

### 1.5 V-모델 레벨 & ASPICE 4.0 (p.189-245)
| 레벨 | ASPICE | Test Basis | 대상/환경 | 수행자 |
|---|---|---|---|---|
| 단위 | **SWE.4** SW Unit Verification | SWE.3 상세설계(단일 unit 동작) | 함수/모듈, Test Harness(Driver+Stub) | 개발자 |
| 통합/컴포넌트 | **SWE.5** SW Component & Integration Verification | SWE.2 아키텍처(컴포넌트 동작+인터페이스) | 인터페이스 불일치, 타이밍/호출순서/공유데이터 | 개발자 or 테스터 |
| 시스템(SW) | **SWE.6** SW Verification | SWE.1 SW 요구사항 | 통합 SW 전체, 기능/비기능, E2E | 독립 팀/제3자 |
| 인수 | VAL.1 Validation | 이해관계자 요구 | 실사용 환경 | 고객/사용자 |
- ASPICE 4.0 BP 공통 골격: 검증 측정(measure) **명세 -> 선택 -> 수행 -> 일관성 + 양방향 추적성 -> 결과 요약/전달** (SWE.4 BP1-5, SWE.5 BP1-7, SWE.6 BP1-5, p.208/224/234). SWE.4 BP1은 **통과/실패 기준, 시작/종료 기준, 필요한 검증 인프라**를 명세하라고 요구(p.245).
- ASPICE 4.0은 "Testing" 대신 "Verification" 용어: 단위 검증은 정적분석+테스트+코드리뷰 조합 가능(p.194). SWE.4 예시 측정: 정적분석, 코드 리뷰, 단위 테스트(p.245). 정적분석은 MISRA 룰셋 기반 가능.
- Unit 정의: "분리 불가한 일관된 동작 + 독립 검증 가능", **C 함수 1개 또는 .c 파일 전체**도 unit(p.198).
- 회귀 검증 기준을 검증 측정 선택(BP2)에 포함해야 함(p.146).
- 환경: 단위/통합은 타겟 우선이나 불가하면 환경 차이 분석 후 후속 단계 보완(p.211, 227). **SIL/PIL/HIL**(p.199): VBC는 SIL(호스트 PC) 수준.

### 1.6 단위 테스트 보조 개념
- **Driver**: 대상 모듈을 호출하고 입력 전달/결과 수집. **Stub**: 대상이 호출하는 하위 모듈을 단순화해 대체(p.205).
- **Test Double**(p.206): Dummy(자리채움) / Stub(미리 정한 값 반환, 상태 검증) / Fake(단순 실제 구현) / Spy(호출 기록) / Mock(기대 호출·횟수 검증, 행동 검증). C 도구: Unity(+CMock) 경량, CppUTest/GoogleTest 중량(p.334).
- **FIRST**(p.207): Fast, Isolated/Independent(실행 순서 무관), Repeatable(환경 무관 동일 결과), Self-validating(자동 Pass/Fail), Timely.
- `assert()` 관례(p.335-337): 제품코드 `src/`, 테스트 `test/`; `foo.c` -> `foo_test.c`; `foo()` -> `testFoo()`; 좌측 실제값, 우측 기대값.
- 테스트하기 좋은 코드(p.137-138): 함수 하나는 하나의 책임, 크기 작게, 의존 분리, **If(A&&B||C)는 함수당 3개 정도(CCN 3 기준)**, 리턴 타입 명시.

## 2. 테스트 설계 기법 (명세 기반 = 블랙박스)

분류(p.246): 명세 기반(입출력만 보고, 모든 레벨) / 구조 기반(소스 로직, 커버리지로 평가) / 경험 기반(직관, 베이시스가 부족할 때). ISO 26262 Part 6은 Table 8(단위 TC 도출 기법)을 요구(p.264). 명세 기반 이점(p.267): 코드 전에 TC 설계 가능(Shift-Left), 명세 모호/누락/불일치 조기 발견, **명세에 있는데 구현 안 된 기능(누락) 검출**에 유효.
- **Positive vs Negative**(p.268): Positive = 유효 입력 happy path, Negative = 무효/예외 입력이 에러 처리되고 비정상 동작을 안 일으키는지. 무효 입출력은 명세에 명시 안 된 것.

| 기법 | 정의 (PDF 근거) | 운용 규칙 |
|---|---|---|
| ① 동치 클래스 분할 (Equivalence Partitioning) p.269-274 | 입력 도메인을 "같게 처리되는 구간"으로 나누고 클래스당 대표값 선택. 유효 범위만 테스트하면 부족(p.270) | **One-to-One**: 클래스마다 TC 1개 이상(독립). **Minimized**: 한 TC가 여러 유효 클래스를 동시 커버해 수 절감. 단 **무효 클래스는 원인 식별 위해 항상 1개씩 독립 테스트**(p.274) |
| ② 경계값 분석 (BVA) p.275-282 | 오류가 몰리는 경계에서 TC 작성 | **2-value**: 경계값 + 경계 바깥 최근접값(10<=x<=20 -> 9,10 / 20,21). **3-value**: 경계값 + 안쪽 + 바깥(9,10,11 / 19,20,21) (p.281) |
| ③ 조합 테스트 / Pairwise p.286-289 | 전 조합은 비현실적 -> 2개 인자 쌍(pair)을 모두 한 번씩 커버하도록 선택. 근거: 대부분의 결함은 2요소 상호작용 | 수작업은 어려워 도구 사용(p.288). 실습: 자동제동(속도3x대상4x노면3x조도3x제어3) |
| ④ 에러 추정 p.290 | 테스터 경험으로 취약 입력 추측(경험 기반) | 슬라이드 본문 이미지 `[보강]`: 0, NULL, 음수, 오버플로, 순서 뒤집힘 |
| 결정 테이블 `[보강]` (PDF 없음) | 조건 조합 x 동작 표. 조건 규칙마다 TC | 다중 조건 -> 결과 매핑이 있는 규칙(L/W/D) 적합 |
| 상태 전이 `[보강]` (PDF 없음) | 상태/이벤트/전이/가드 표 + 유효/무효 전이 | 타이머 유지/해제 로직 적합 |
| 원인-결과 그래프/기능 테스트 | PDF에 해당 슬라이드 없음 | - |

실습 예(p.272-285): 멤버십 등급 경계(200만/100만/50만/0원), 자동결제 기간(6/12/18개월, 최대 24) -> "VVIP 경계값 TC 12개 도출", 삼각형 유형(유효/무효 분할 + 경계). 즉 **임계값 N개 -> 경계마다 2~3 TC + 무효 영역 TC**가 기본 산출 방식.

### 리스크 기반 테스트 (p.148-155)
- 위험 = 발생가능성 x 영향(= 사용 빈도 x 결함 가능성, Reynolds). 요소 점수 9/5/3/1/0.
- 영역 매핑(p.154-155): 영향 큰+가능성 큰 STA는 **공식 테스트 설계 + 경계값 + 완전 코드 인스펙션 + 문장 커버리지 100%**, 낮은 영역은 자유 테스트. -> VBC에서 안전 관련 모듈(문 잠금 D, 센서 고장 C)에 기법을 두껍게.

### 경험/기타
- 모델 기반 테스트(MBT, p.156): 정형/반정형 모델에서 TC 자동 생성; 안전필수에 적합, 초기 비용 큼. VBC 규모에선 상태표를 표로만 두고 수작업 변환 권장.
- 회귀 테스트(p.143-147): 수정 후 **확인 테스트(실패했던 TC 재실행, 발견자가 수행)** + **회귀 테스트(부작용 확인)**. 전략: Retest-all / 선택(영향도 분석) / 최소화 / 우선순위화. 자동화 + 커밋/일 단위 주기 + CI 연계 권고. 테스트 자동화 = "수행의 자동화"이며 TC는 사람이 설계(p.133).

## 3. 커버리지 / 구조 기반 기법 (화이트박스)

- 커버리지 = 테스트가 대상을 몇 % 실행했나. **요구사항 커버리지**(블랙박스용: 예 30개 요구 중 몇 개 테스트) vs **소스 커버리지**(화이트박스용: 문장/결정) (p.180, 295).
- 구조 기반은 전 경로 대신 일부만 테스트(p.296). 종류 8개(p.296):

| 기법 | 충족 조건 (PDF) | 비고 |
|---|---|---|
| 기본 경로 (Basis Path) p.298-304 | CFG 작성 -> 순환복잡도 CC 계산 -> 독립 경로 CC개 정의 -> TC | **CC = E-N+2 = P+1 = R**. 예: 성적 프로그램 CC=3 -> 최소 독립 경로 3개 |
| 함수 p.305-307 | 모든 함수가 한 번 이상 호출 | |
| 문장 (Statement) p.308 | 실행 가능한 모든 문장 1회 이상. 100% = 전부 실행 | 가장 약함 |
| 결정 (Decision) p.312 | 모든 결정의 True/False 결과 각 1회 | Statement보다 강함: if의 거짓(암시적 else) 영역도 요구(p.316-317). 29119는 Branch(CFG 간선)와 Decision을 구분(p.313) |
| 조건 (Condition) p.318 | 개별 조건식(원자 조건)의 T/F 각 1회 | 결정 결과는 보장 못 함 |
| 조건/결정 p.319 | 결정 결과 + 개별 조건 결과 모두 | |
| **MC/DC** p.323 | 각 개별 조건이 **다른 조건을 고정한 채** 결정 결과에 독립적으로 영향을 준 사례가 최소 1번씩 | 조건 n개 -> 최소 n+1 TC. 실습: `if (a && b \|\| c)` (p.326). C용 도구는 자동 측정(p.327) |
| 다중 조건 p.324 | 조건식의 모든 T/F 조합 | 2^n, 포함 관계 최강(p.297) |

- 포용(Subsumption, p.297): 다중 조건 > MC/DC > 조건/결정 > 결정 > 문장. 상위 100%이면 하위도 100%.
- ISO 26262 Part 6 Table 9(단위 구조 커버리지) 목표 %: PDF에서 이미지(p.328)라 값 없음. `[보강]` 일반적으로 ASIL A/B는 문장(+분기), C/D는 분기 + MC/DC 권고.
- **MC/DC 예 `[보강]` (a && b || c)**: (a,b,c)=(T,T,F)->T / (F,T,F)->F (a 독립) / (T,F,F)->F (b 독립) / (F,F,T)->T 와 (F,F,F)->F (c 독립) -> 4~5개 TC.
- 코드 정적 보조: **순환복잡도 기준 p.124**: 1-10 양호, 11-20 다소 복잡, 21-50 고위험, 50+ 테스트 불가. 도구: Lizard(`lizard -C 10`), CPD(중복), cppcheck(p.114, 128-131). **MISRA C:2012**(p.80-90): 단일 return, malloc 금지, 변수 초기화, 전역 최소화, 포인터 제한, 암묵 형변환 금지, goto/재귀 금지. 위반 불가 시 주석으로 사유(Justification) 기록(p.111).

## 4. 테스트 케이스 작성 규칙 / 추적성 / 결함 관리

### 4.1 테스트 케이스 (p.170, 261-262)
- 정의(IEEE 610): 특정 요구가 구현됐는지 확인하려고 **테스트 조건, 입력값, 예상 출력, 실제 결과**를 기록한 것.
- PDF 양식 필드: TC ID / 목적 / 사전조건 / 테스터 / 일자 / 단계 / 입력값 / 예상 출력 / 실행 결과 / 디버깅 필요 / 조치 후 결과.
- 구조 기반 TC 양식(p.307-315): `ID | Coverage 종류 | 관련 함수 | 입력값 | 기대결과(return)`.
- 작성 시점: **테스트 베이시스 작성 시점에 같이 설계** -> 베이시스 품질도 개선 (p.171-172). 개발 시작과 동시에 테스트 활동 시작.
- 판정: 실제 출력 == 예상 출력이면 Pass, 아니면 Fail(고장 발생 -> 결함 추적, p.173). 예상값은 **명세에서 도출**, 코드 실행 결과로 정하지 말 것.
- 용어(p.174, 188): Testware, Test Suite(같은 목표 TC 집합), Scenario, Data, Procedure(재현 가능하게 구체적), Script(자동화용), Harness(실행/제어 도구 묶음).
- 시작/완료 기준(p.175-179, ETVX: Entry/Task/Verification/eXit): 객관적 기준으로 정의. 완료 기준 지표(p.181): **테스트 수행률/성공률/실패율**, 결함 수/조치율, 커버리지. ISO 26262: **테스트 성공 + 요구사항 커버리지 측정**(p.182).

### 4.2 추적성 (p.33, 169, 210, 228, 237)
- ASPICE 4.0: 각 레벨에서 **양방향 추적성 + 일관성**(BP "Ensure consistency and establish bidirectional traceability"). 요구(SWE.1)<->SWE.6 TC, 아키텍처(SWE.2)<->SWE.5, 상세설계(SWE.3)<->SWE.4. TC <-> 테스트 결과도 연결.
- 테스트 계획서 양식에 "테스트 추적 매트릭스"와 "통과 기준" 항목(p.165).
- 결함은 문제 해결 프로세스 SUP.9로 연결: 식별/기록 -> 원인·영향 -> 시작 -> 종결 추적 -> 보고(p.347-348).

### 4.3 결함 관리 (p.349-355)
- 결함 보고서 항목: 컨텍스트(대상/환경/절차/TC/데이터), 기대 vs 실제 차이, 영향, 심각도/우선순위, 위험 분석, 상태.
- 상태 흐름: Open -> Review -> Assigned -> Resolved(Fixed / Won't fix / Duplicated / Invalid) -> Verified -> Closed, + Deferred, Reopen(p.354-355). **Invalid = TC 자체의 결함**.
- 정적분석/리뷰 위반 양식(p.352): 기준, 위반 요약, 위치, 시정 계획, 대상 버전(commit 해시 등). 커밋 메시지에 이슈 번호 `#521 제목`(p.365).

### 4.4 리뷰 (p.52-74)
- 리뷰 유형: 관리/기술/인스펙션/워크쓰루/감사. 인스펙션은 공식(역할: 중재자·낭독자·기록자·작성자, **관리자 참여 금지**), 워크쓰루는 작성자가 기록자 가능. 데스크 체크 = 가장 비공식 동료 검토(p.66).
- 주의사항(p.63-64): **한 번에 200-400 LOC, 300-500 LOC/시간 이하**, 작성자가 사전 주석, 정량 목표, **지적 결함이 실제 수정됐는지 검증**, 일부(20-30%)만 봐도 Ego Effect. 체크리스트는 1페이지 이내, 명령형 항목, 결함 분석으로 갱신(p.62).
- ISO 26262 리뷰 대상: 아키텍처, 상세 설계, 소스코드(p.67).

## 5. VBC 적용

### 5.1 레벨 매핑
| 대상 | ASPICE 개념 | VBC 대응 |
|---|---|---|
| 함수 1개/모듈 단위(`headlight_update` 등) | SWE.4 | `tests/test_*.c` 모듈별 단위 테스트, **Driver = test main, Stub = 센서/클럭 입력 주입** |
| 모듈 간(조명-공통 규칙 C, 문 잠금-대시보드 경고) | SWE.5 | 모듈 결합 테스트(신호 단절이 하위 모듈 결과에 전파되는지) |
| VBC-SRS-001 시나리오 전체(L+W+D+C) | SWE.6 | 요구사항 단위 시나리오, verification.md로 추적 |
| 코드 리뷰 + 컴파일 경고/cppcheck/lizard | SWE.4 정적 측정 | cross review가 곧 정적 검증 측정 |

- **주입 가능한 클럭** = Stub/Test Double 개념(FIRST의 Repeatable/Fast 충족: 실제 sleep 없이 시간을 진행). `clock_advance(2900)` 식으로 제어.
- 가상 환경이므로 SIL 수준. PDF 권고(p.211): 타겟 불가 시 환경 차이를 문서화. -> verification.md에 "HW 미사용, SIL"이라 명시.

### 5.2 기법 <-> 모듈 선택표
| 모듈/요구 | 1순위 기법 | 보조 | 커버리지 목표 |
|---|---|---|---|
| C1/C2 N초 유지·0.5s 신호 단절 | **BVA(시간)** + 상태 전이 `[보강]` | Negative(신호 끊김/재개) | 결정/분기 100% |
| L2(1s)/L3(3s) 등 N초 연속 유지 타이머 | BVA(시간) + 상태 전이(타이머 리셋 조건) | 조합(조도 x 모드) | 분기 100%, 타이머 리셋 경로 |
| L1-L6 조명 규칙(여러 조건 AND/OR) | **결정 테이블** `[보강]` + 동치 분할 | Pairwise(입력 인자 많을 때) | **MC/DC** 후보 |
| W2 임계 10/40/70% 구간 | **동치 분할 + 3-value BVA** | 구간별 출력 표 | 결정 100% |
| D3 속도 >= 15 | BVA 3-value | 경계 + 무효(음수/센서 고장) | 결정 100% |
| C3 속도 0~250 범위 유효성 | **동치(유효1+무효2) + BVA** | NaN/센서 고장 값 | 결정 100% |
| D1-D5 문 잠금·경고 | 결정 테이블 | 상태 전이(잠금/해제) | MC/DC 후보(안전 관련) |
| 전 모듈 | 에러 추정 | 회귀 | 문장 100%(최소 기준, p.155) |

권고 우선순위: 안전 관련(문 잠금/센서 고장/신호 단절)은 리스크 높음(p.154-155) -> 공식 기법 + 분기/MC-DC + 코드 인스펙션. 위험 낮은 편의 기능은 문장 커버리지 + 대표 시나리오.

### 5.3 BVA 구체 예 (PDF 3-value 규칙: 경계 -1tick/경계/+1tick)
시간 단위가 ms 클럭이라면 "1 tick" = 1ms (혹은 클럭 해상도). 아래 값은 **판정 연산자가 `>=`인지 `>`인지 SRS에서 먼저 확정**하고 기대값을 작성할 것(경계 TC의 핵심 목적이 바로 이 구분).

| 요구 | 경계 | TC 입력(경계 주변) | 기대(연산자 `>=` 가정) |
|---|---|---|---|
| C2 0.5s 신호 단절 | 500ms | 단절 후 499ms / 500ms / 501ms 경과 | 499: 정상 유지, 500·501: 고장(fault) 판정 |
| N초 연속 유지 (C1, 예 3s: L3) | 3000ms | 유지 2900 / 2999 / 3000 / 3001 | 2999까지 미발동, 3000에 발동 |
| 위 타이머 + 중단 | 2900ms 후 조건 해제 -> 재충족 | 2.9s 유지 -> 0.1s 해제 -> 다시 0.2s | **리셋 확인**: 재충족 후 3.0s 경과 전 미발동 (경과 합산 버그 검출) |
| L2 1s | 1000ms | 999 / 1000 / 1001 | 위와 동일 패턴 |
| W2 임계 10% | 10 | 9 / 10 / 11 | 구간 전이 확인 |
| W2 임계 40% | 40 | 39 / 40 / 41 | |
| W2 임계 70% | 70 | 69 / 70 / 71 | 구간 3개 경계 모두 + 구간 내부 대표값(예 5, 25, 55, 85) |
| D3 속도 >= 15 | 15 | 14 / 15 / 16 (float이면 14.99, 15.0, 15.01) | 14: 미동작, 15: 동작 |
| C3 속도 0~250 | 0, 250 | -1 / 0 / 1 / 249 / 250 / 251 | -1, 251: 무효 처리(오류 플래그/기본값), 0..250: 유효 |

- **동치 분할(C3)**: 유효 [0,250] 1개 + 무효 `<0`, `>250` 2개 + (명세에 있다면) NaN/미수신. 유효는 대표값 1개로 Minimized, **무효는 반드시 개별 TC**(p.274).
- **Pairwise**: L1-L6 입력이 (조도 구간 x 와이퍼/라이트 모드 x 속도 구간 x 센서 정상/고장)처럼 4개 이상 인자일 때, 전수 대신 쌍 커버(p.287-289 방식). 안전 관련은 전수 + 결정 테이블이 우선.
- **MC/DC 실습**: `if (a && b || c)` 패턴이 VBC 조건문(`door_open && speed>=15 || fault`) 구조와 동일 -> 위 `[보강]` 4~5 TC 구성 사용.
- **Negative TC**: 신호 단절 중 값 변화, 범위 밖 값, 센서 고장 직후 복귀, 타이머 진행 중 입력 변경.

| Req ID | TC ID | 기법/목적 | 사전조건/클럭 | 입력(시나리오) | 기대 결과 | 실제 결과 | Pass/Fail | 증거 | 작성자 | 검증자 |
|---|---|---|---|---|---|---|---|---|---|---|
| C2 | TC-C2-01 | BVA 3-value (499ms) | t=0, 신호 정상 | 신호 손실 후 +499ms | fault 미판정 | (실행 후 기록) | | test_common.c::test_c2_499 | A | B |
| C2 | TC-C2-02 | BVA (500ms) | 동일 | +500ms | fault 판정 | | | test_c2_500 | A | B |
| W2 | TC-W2-04 | 동치/BVA (39/40/41) | 와이퍼 AUTO | 강우 센서 39% / 40% / 41% | 단계 N / N+1 | | | | | |
| D3 | TC-D3-02 | BVA (속도 15) | 시동 ON, 기어 D, 잠금 해제 | 유효한 속도 14 / 15 | 직전 상태 유지(해제) / 잠금 | | | | | |
| D4 | TC-D4-02 | BVA (속도 0 / 1) | 문 하나 열림 | 유효한 속도 0 / 1 | 경고 없음 / "주행 중 도어 열림" | | | | | |
- 규칙(PDF 반영): 요구사항 1개당 최소 1 정상 + 1 경계 + 1 무효 TC. **기대 결과는 SRS에서 먼저 도출**하고 코드 결과로 채우지 말 것(p.37 예제: 우연히 맞는 입력 주의). Req <-> TC <-> evidence 3자 추적성이 ASPICE BP4(양방향)에 해당. 요구에 TC가 하나도 없으면 요구사항 커버리지 구멍(수행률/성공률/커버리지로 관리, p.181).
- 증거(evidence)는 실행 로그/assert 결과/커밋 해시. 자동 판정(Self-validating)으로 사람 눈 비교를 줄일 것(FIRST).

### 5.5 팀 규칙과의 연결
- **author != verifier**: 원리 "객관성" + ISO 26262 리뷰 요건. 인스펙션처럼 **작성자는 설명만, 수정 논의는 회의 밖**(p.71), **지적 사항이 실제 수정됐는지 확인**(p.64 #5). 체크리스트: 요구가 모두 구현됐는가 / 변수 초기화 / 무한 루프 조건 / 경계 `>=` vs `>` / 단일 return / 매직 넘버(p.61).
- **AI mistakes 로그**: 결함 보고서 항목 차용(컨텍스트, 기대 vs 실제, 원인, 상태). 분류에 Mistake(원인) -> Fault -> Failure 구분(p.39), 결과 처리 유형 Fixed/Won't fix/Duplicated/**Invalid(TC가 틀림)**(p.355). AI가 만든 TC의 기대값 오류는 Invalid에 해당, 반복되면 체크리스트로 승격(p.62: 체크리스트는 결함 분석으로 갱신).
- **수정 후**: 확인 테스트(실패했던 TC) + 전체 회귀 실행(p.143-147). VBC는 규모가 작으므로 **커밋마다 전체 `tests/` 실행**(p.147).
- 한계 명시: 테스트는 결함 부재를 증명하지 못함(원리 1) - verification.md에 "통과 = 정의된 TC 범위에서 요구 충족"으로 서술.
