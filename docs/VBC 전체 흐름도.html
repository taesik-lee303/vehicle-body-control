VBC 전체 흐름도

작업 폴더 vbc-sim-exp의 src/ 파일 15개가 어떻게 이어지는지 한 장에 그렸습니다. 큰 흐름은 세계 → 감지 → 인지 → 판단 → 실행 → 다시 세계이고, 이 고리를 console.c가 50 ms마다 한 바퀴씩 돌립니다. 모든 판단 모듈은 common이 만든 VbcContext를 공통 입력으로 봅니다.

제품 코드 (실차에 그대로 올라감) 시뮬레이터 · 팀원 차체 모듈 레이더 ↔ 제품 규격 차량 모델 호출 · 데이터 VbcContext 브라우저 → 세계 (경로 · 자차 자세) 요청 다음 주기로 되돌아감

50 ms 한 바퀴

터미널의 wait나 브라우저의 sim_advance()가 시간을 넘기면 console_advance()가 50 ms마다 아래를 반복합니다. 4~5번은 adas on일 때만 돕니다.

  1. drive_step() drive.c · 실행 지난 주기에 받은 요청과 페달로 속도를 바꾸고, 그 값을 panel.speed에 씁니다.
  2. send_signals() → vbc_rx_*() console → common 패널 값(속도·기어·시동·조도·강우)을 이번 시각으로 다시 보냅니다. cut으로 끊은 신호는 빠집니다.
  3. vbc_step() vbc → common → 차체 4개 vbc_build_context()로 VbcContext를 만들고 와이퍼 → 조명 → 도어 → 계기판을 부릅니다.
  4. adas_tick() console world_step()으로 세계를 움직이고, 레이더 3대마다 radar_sim_frame() → map_rx_frame(), 이어서 map_set_yaw_rate() → map_step().
  5. adas_control() console sg_step()이 정한 가속도·정지 유지를 drive_set_request()로 넘깁니다. 속도는 다음 바퀴의 1번에서 바뀝니다.
  6. report_changes() console 바뀐 판정·출력·선행 차량·Stop & Go 상태를 로그에 찍습니다.

Console 안의 구조체

프로그램의 모든 상태는 Console 하나에 들어 있습니다. 함수들은 이 안의 자기 칸 주소만 받아 일합니다. 예를 들어 sg_step(&a->sg, …)은 Stop & Go 칸만 받습니다.

실제 레이더 제품과 비교

RADAR_MOUNTS 제원을 실제 제품에 맞대 본 것

우리 레이더 구성과 가장 비슷한 실제 제품은 앞쪽 Continental(현재 AUMOVIO) ARS548 RDI 하나와 모서리 SRR520 두 개입니다. 장착 방식(앞 범퍼 모서리, 바깥쪽 45°)도 실제 차의 모서리 레이더 배치와 같습니다.

가장 닮은 점: 트랙이 아니라 검출점을 받는다는 것입니다. 보통 차량용 레이더는 안에서 추적까지 끝낸 물체 목록을 줍니다. ARS548은 점 목록도 내보내기 때문에, 우리 adas_map처럼 군집화와 추적을 직접 짜는 구조가 됩니다. 연구용 데이터셋과 ROS 드라이버에도 많이 쓰입니다.

다른 점 1 · 고도 시야: ARS548의 고도 시야는 아직 확인하지 못했습니다. 찾은 숫자(±70°)는 판매 사이트에서 옮겨 적은 값이고 공식 데이터시트에서는 값을 읽지 못해, 우리 값 ±15°와 맞는지 아직 모릅니다. 고도 빔폭은 2.3°라서 우리 고도 분해능 2°와 비슷합니다.

다른 점 2 · 현실 잡음: 실제 레이더는 다중 경로 반사, 같은 대역 다른 레이더의 간섭, 비 때문에 생기는 감쇠가 있습니다. env_radar는 이것을 넣지 않고 산란점, 검출 확률, 가림, 잡음, 클러터만 흉내 냅니다.

다른 점 3 · 점 개수: 검출점 최대 개수 512 / 128은 우리가 정한 값입니다. SRR520의 최대 검출점 수는 공개 자료에서 찾지 못했습니다.
