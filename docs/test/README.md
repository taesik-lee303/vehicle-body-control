# 모듈별 테스트 (신호 주입기)

실제 차량을 시험한다고 보고, 도어·계기판·조명·와이퍼 모듈을 **하나씩** 시험합니다.
테스트 근거와 용어는 `docs/ref/sw-testing.md`(강의 교재 정리)를 따릅니다.

| 문서 | 내용 |
|---|---|
| 이 문서 | 원칙, 도구 사용법, TC 작성법, 발견 사항, 한계 |
| `docs/test/tc-results.md` | **실행한 TC와 결과 (자동 생성)** |
| `docs/test/logs/<모듈>.log` | 실행 로그 = 증거 |
| `tools/consoles/tc/<모듈>.txt` | TC 정의 (입력과 기대값) |

## 1. 원칙: 테스트 도구는 입력을 거르지 않는다
교재 p.45 "비정상/예외 입력도 테스트", p.268 Negative TC "무효·예외 입력이 **제품 코드에서** 처리되는지 확인".
테스트 도구(Driver, p.205)가 입력을 걸러 버리면 제품 코드는 그 상황을 한 번도 받아 보지 못하고, 실제 차량에서 그런 신호가 오면 대응할 수 없습니다.

| 구분 | 역할 | 이 저장소 |
|---|---|---|
| 테스트 도구 (`tools/consoles`) | 신호 형식(정수)으로 표현할 수 있는 값은 **무엇이든 그대로** 보내고, 시간·송신 시각을 마음대로 정한다 | 신호 주입기 |
| 입력 판정 (`src/common.c`) | 원래 코드를 그대로 받고, 유효·고장·수신 중단을 **명시적으로** 판정한다 | C2·C3·C4, 코드 정의 여부(`*_valid`) |
| 각 모듈 (`src/*.c`) | 판정 결과를 받아 요구사항대로 동작한다 | 도어, 계기판, 조명, 와이퍼 |

넣을 수 **없는** 값은 신호 형식으로 표현이 안 되는 것뿐입니다: 소수(`50.5`), 글자(`abc`), int32 밖. 차량 신호는 정해진 비트의 정수라 이런 값은 실제로도 오지 않습니다.

이 원칙에 맞춰 `common.h`도 바꿨습니다 (2026-10-08). 전에는 시동을 `bool`로 받아 코드 2가 **타입 변환으로 몰래 "켜짐"**이 되었고, 기어·스위치는 enum 변수에 담겨 음수가 다른 숫자(4294967295)로 바뀌었습니다. 지금은 원래 코드를 그대로 저장·전달하고, 정의된 코드인지는 `ctx->ignition_valid`, `gear_valid`, `door_valid[]`, `light_sw_valid`, `wiper_sw_valid`로 드러냅니다. **정의 안 된 코드일 때 무엇을 할지는 사양서에 없으므로 동작은 바꾸지 않았습니다** (5절 질의 후보).

## 2. 실행
```bash
make test        # 기존 단위 테스트 (코어·모듈)
make tc          # 모듈별 TC 전체 실행 → docs/test/tc-results.md, docs/test/logs/*.log 갱신
make con-doors   # 대화형: con-dashboard, con-lighting, con-wipers
make con-ecu     # 대화형: BCU 전체 (SWC 4개 연동)
./build/con_doors < tools/consoles/tc/doors.txt     # TC 파일 하나만
```
`make tc`는 FAIL이 하나라도 있으면 실패(종료 코드 1)합니다.

## 3. 신호 주입기 명령
모든 콘솔에서 같은 명령을 씁니다. 메뉴 번호를 골라도 됩니다. `h`로 전체 목록을 볼 수 있습니다.

| 명령 | 뜻 |
|---|---|
| `ign 1`, `gear d`, `speed 15`, `lux 70000`, `rain -1` | 주기 신호 값. **아무 정수**(int32)나 넣을 수 있음. 바꾸면 그 시각에 바로 보냄 |
| `fl 1`, `fr open`, `rl 2`, `rr -1` | 도어 4개 (0 닫힘, 1 열림, 그 밖의 코드도 그대로) |
| `light auto`, `light 7`, `wiper high`, `wiper -1` | 스위치 (이름 또는 아무 코드) |
| `level low`, `level 9` | 조명 콘솔 전용: L6에 넘길 와이퍼 단계 (와이퍼 모듈은 실행하지 않음) |
| `lock on`, `lock off` | 도어 콘솔 전용: **직전 잠금 상태**를 바로 넣음. 잠금은 사양서 입력이 아니라 모듈 상태라 0/1만 됨. 넣은 시각에 바로 판단하므로 시동 OFF·기어 P면 곧 풀림(D2) |
| `t 0.499` | 시간 진행, **1ms 단위** |
| `cut speed`, `cut vehicle`, `cut all` | 송신 끊기 (신호마다 따로. vehicle = 속도·기어·시동) |
| `resume speed` | 송신 다시 시작 (그 시각에 바로 보냄) |
| `send gear` | 지금 **한 번만** 보내기 |
| `auto off` | 자동 재송신 끄기 (`send`와 함께 송신 시각을 직접 정함) |
| `period step 10`, `period send 200` | 판단 주기(기본 1ms), 자동 송신 주기(기본 50ms) |
| `tc ID \| 요구사항 \| 기법 \| 입력 \| 기대` | TC 시작 (이후의 `e`/`obs` 결과가 이 TC에 묶임) |
| `e lock on`, `e warning door`, `e rxlost yes` | 기대 확인 → PASS/FAIL |
| `obs lock` | 관찰만 기록 (사양서에 정해지지 않은 동작) |
| `r` | 처음 상태(C5), 시각 0 (진행 중인 TC는 이어짐) |
| `show`, `q` | 지금 상태, 종료 |

`e`/`obs` 항목: 출력 `lock headlight luxlamp rainlamp`(on/off), `wiper`(stop/int/low/high), `warning`(none/door/lux/rain),
판정 `rxlost ignon speedvalid luxfault rainfault ignvalid gearvalid doorvalid lightvalid wipervalid`(yes/no).

화면의 `→ [0.500s] (판정) 수신 중단: 아니오 → 예`처럼 출력과 판정이 바뀐 순간이 1ms 단위로 찍힙니다.

## 4. TC 작성 규칙 (교재 5.3·5.4)
- **기대값은 사양서에서 먼저 계산**합니다. 코드를 돌려 본 결과로 채우지 않습니다 (p.37, 5.4).
- 요구사항마다 정상 + 경계 + 무효를 최소 1개씩 둡니다 (5.4).
- 경계는 **3-value**: 기준 직전 / 기준 / 직후 (예: 499 / 500 / 501 ms, 14 / 15 / 16 km/h, 9 / 10 / 11 %).
- 무효 클래스는 원인을 알 수 있게 **한 TC에 하나씩** 넣습니다 (p.274).
- 사양서에 동작이 정해지지 않은 입력은 `e`가 아니라 **`obs`로 관찰만** 남기고 질의 후보로 올립니다 (사양서 7장).

TC 파일 예 (`tools/consoles/tc/doors.txt` 일부):
```
tc TC-D1-01 | D1, C4 | 경계값(시간 3-value) | D, 30으로 잠근 뒤 속도 신호만 끊기, 0.499초 | 수신 중단 아님, 잠김
r
ign on
gear d
speed 30
cut speed
t 0.499
e rxlost no
e lock on
tc TC-D1-02 | D1, C4 | 경계값(시간 3-value) | 이어서 +1ms (0.500초) | 수신 중단, 잠김 유지
t 0.001
e rxlost yes
e lock on
```
새 TC를 파일에 추가하고 `make tc`를 돌리면 `tc-results.md`에 자동으로 들어갑니다.

## 5. 발견 사항: 질의 후보 Q8~Q11
신호 주입기로 정의 안 된 코드를 넣어 처음 드러난 동작입니다. **사양서에 처리 방법이 없어서 결함인지 아닌지 판단할 수 없습니다.** 고객(강사)에게 질의하고, 답에 따라 `common.c`나 모듈을 고칩니다. (`docs/c-structure.md` 질의 후보 표에도 추가)

| # | 입력 | 지금 동작 (관찰) | 걱정되는 점 | TC |
|---|---|---|---|---|
| Q8 | 기어 코드가 P/R/N/D가 아님 (7, -1) | 기어 무효로 판정되지만 도어는 "P가 아님"으로 취급 → 15 km/h 이상이면 잠기고, **정차해도 풀리지 않음** | 기어 신호가 깨지면 문이 잠긴 채 남을 수 있음 | TC-D-Q8-01~03, TC-E-Q8-01 |
| Q9 | 시동 코드가 0/1이 아님 (2, -1) | 0이 아니면 **켜짐**으로 봄 → 전조등·와이퍼 동작, 도어는 시동 OFF 해제(D2)가 안 됨 | 시동 신호가 깨졌는데 정상 켜짐처럼 동작 | TC-D-Q9-01·02, TC-L-Q9-01, TC-W-Q9-01 |
| Q10 | 도어 코드가 0/1이 아님 (2, -1) | 0이 아니면 **열림**으로 봄 → 주행 중 도어 열림 경고 | 도어 센서 이상을 "열림"으로 볼지 "고장"으로 볼지 | TC-E-Q10-01·02 |
| Q11 | 조명 스위치 코드가 OFF/AUTO/ON이 아님 (7, -1) | 조도 판단(L2·L3)은 하지 않아 **직전 상태 유지**, 그런데 **와이퍼 판단(L6)은 적용**되어 켜짐 | 같은 값을 L2·L3은 AUTO 아님으로, L6은 AUTO처럼 다룸 (일관성 없음) | TC-L-Q11-01·02 |
| (참고) | 와이퍼 스위치 정의 밖 코드 | 팀 요구사항 SWR-W4-005대로 **마지막 정상 값 유지** (PASS) | 팀이 정해 둔 경우. Q11도 이렇게 정할지 검토 | TC-W-SWR-01·02 |
| (참고) | 조명에 넘어온 와이퍼 단계 코드 9 | "작동 중"으로 봄 (L6) | 와이퍼 모듈은 0~3만 내보내므로 실제로는 생기지 않음. 모듈 간 약속 확인용 | TC-L-IF-01 |

## 6. TC가 결함을 잡는지 확인 (일부러 결함을 넣어 보기)
모든 TC가 PASS여도 TC가 약하면 의미가 없습니다 (p.37 "우연히 맞는 입력"). 모듈 코드에 결함을 하나씩 넣고 TC를 돌린 뒤 원래대로 되돌렸습니다 (2026-10-08).

| 넣은 결함 | 잡은 TC |
|---|---|
| 도어 D3 `>= 15`를 `> 15`로 | TC-D3-02, D3-08, D3-09 |
| 도어 D1 수신 중단 처리 제거 | TC-D1-02, D1-03, D1-04 |
| 도어 D2 기어 P 조건 제거 | TC-D2-01, D2-03 |
| 계기판 D4 `> 0`을 `>= 0`으로 | TC-D4-01 |
| **계기판 D4 유효한 속도 조건 제거** | **잡지 못함** (아래 한계 1) |
| 조명 L2 1초를 0.999초로 | TC-L2-01, L2-04, L2-06 |
| 조명 L3 1500 초과를 1499 초과로 | TC-L3-03 |
| 조명 L6 10초를 9초로 | TC-L6-01 |
| 와이퍼 W2 40%를 41%로 | TC-W2-02, W3-01 |
| 와이퍼 W3 유효한 속도 조건 제거 | TC-W3-03 |
| 공통 C2/C4 0.5초 `>=`를 `>`로 | TC-D1-02, D1-06 |

## 7. 이 방식의 한계
1. **입력은 항상 `common.c`를 거칩니다.** 그래서 `common.c`가 만들지 않는 판정 조합(예: 유효한 속도가 아닌데 속도 값이 30)은 넣을 수 없습니다. 계기판의 "유효한 속도 조건 제거"를 못 잡은 이유입니다(코어가 무효 속도를 0으로 넘겨서 결과가 같음). 이런 경우는 판정 결과(`VbcContext`)를 직접 만들어 모듈을 부르는 단위 테스트(`tests/test_*.c`)로 시험해야 합니다.
2. **한 모듈씩만** 실행합니다. 모듈 사이 연결(실제 와이퍼 → 조명 L6 등)은 `make scenarios`나 시뮬레이터(develop 브랜치)로 확인합니다.
3. 호스트 PC에서 도는 **SIL** 수준입니다 (교재 1.5). 실제 ECU의 실행 시간·인터럽트·메모리 제약은 다루지 않습니다.
4. 결과 문서의 TC는 제가(Claude Code) 설계·실행한 것입니다. **만든 사람 ≠ 검증하는 사람** 원칙에 따라 팀원이 TC 자체를 리뷰해야 합니다 (기대값이 사양서에서 맞게 계산됐는지 포함).

## 8. 직접 시험할 때 찾아볼 관점
`tc-results.md`의 "요구사항별 TC" 표에서 TC가 적은 곳부터 보세요. 교재의 기법별로 아래를 스스로 물어보면 빈 곳이 보입니다.
- **결정 테이블**: 우선순위(L1 > L5 > L4 > L6 > L2·L3, W1 > W4 > W5 > W2·W3, D1 > D2 > D3)의 조건 조합을 모두 덮었나?
- **상태 전이**: 타이머가 도는 중에 다른 입력이 바뀌면? 무효한 전이는?
- **경계값**: 모든 임계값(시간, 조도, 강우, 속도)에 3-value가 있나? 범위 끝(0, 250, 60000, 100)은?
- **에러 추정**(p.290): 0, 음수, 최댓값(2147483647), 최솟값, 같은 값 반복, 순서 뒤집힘
- **타이밍**: 송신 간격이 0.5초에 가깝거나 넘는 경우(`period send 499`, `period send 500`), 끊겼다 바로 돌아오기, `auto off` 후 들쭉날쭉 보내기, 판단 주기를 늘린 경우(`period step 10`)
- **시작 직후**: 처음 값이 들어오기 전(0~0.5초)의 판정
- **MC/DC**(p.323): 조건이 여럿인 판단에서 조건 하나만 바꿔 결과가 바뀌는지

찾은 TC는 `tools/consoles/tc/<모듈>.txt`에 추가하고 `make tc`로 결과 문서에 반영합니다. 사양서와 다르게 동작하면 결함으로, 사양서에 없는 동작이면 질의 후보로 기록합니다.
